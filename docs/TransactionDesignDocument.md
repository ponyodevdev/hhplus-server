# STEP 16. Transaction Diagnosis
- 서비스 확장 시, 어플리케이션 서버와 DB를 도메인별로 분리했을 때 트랜잭션 처리의 한계와 대응 방안

---

## 1. 도메인 및 배포 단위 분리

서비스가 확장됨에 따라 업무 성격에 따라 도메인과 데이터 저장소를 분리한다.  
이렇게 하면 성능, 유지보수성, 장애 격리 측면에서 유리하다.

- **예약 서비스**
    - 좌석 배정, 예약 생성과 취소
    - Reservation DB

- **결제 서비스**
    - 결제 승인과 취소, 거래 기록 관리
    - Payment DB

- **포인트 서비스**
    - 포인트 충전과 사용, 잔액 관리
    - Point DB

➡ 배포 단위가 도메인별로 분리되어 기능 확장 및 장애 격리에 강하다.  
➡ 단일 DB에 모든 기능을 몰아넣는 대신, 업무별 DB로 분리해 책임이 명확해진다.

---

## 2. 트랜잭션 분리에 따른 한계

도메인별 DB가 분리되면 기존의 단일 트랜잭션과 달리, 여러 DB에 걸친 원자적 처리 보장이 어렵다.

### (1) 원자성 깨짐
- 하나의 사용자 요청이 여러 DB에 걸쳐 실행될 때 일부만 성공하거나 실패할 수 있다.
- 예: 좌석 예약은 성공했지만 결제 DB 반영 실패 → 좌석만 점유된 상태 발생

### (2) 정합성 손실
- 결제는 승인되었는데 포인트 차감이 실패 → 사용자 금액과 포인트 내역 불일치 발생

### (3) 분산 트랜잭션의 한계
- 분산 트랜잭션을 쓰면 가능하긴 하지만
    - 성능 저하
    - 장애 시 복구 어려움
    - 클라우드 환경에서 적합하지 않음

---

## 3. 대응 방안

### (1) 이벤트 기반 SAGA 패턴
- 각 서비스는 자기 DB 트랜잭션만 책임진다.
- 상태 변경 후 이벤트 발행 → 다른 서비스가 이벤트를 구독해 자기 DB에 반영한다.
- 보상 트랜잭션을 두어 실패 시 되돌림.
    - 예: 결제 실패 → 예약 취소 이벤트 발행
    - 예: 포인트 차감 실패 → 결제 취소 이벤트 발행

➡ 분산 트랜잭션 대신 최종 일관성을 확보한다.

### (2) Outbox 패턴
- 이벤트 발행 시 Outbox 테이블에 함께 기록한다.
- 별도 프로세스가 Outbox 테이블을 읽어 메시지 브로커로 발행한다.
- DB 커밋과 이벤트 발행의 원자성을 보장한다.

➡ 이벤트 유실을 막고 재처리가 가능하다.

### (3) CQRS와 이벤트 소싱 (확장 고려)
- 쓰기와 읽기를 분리한다.
- 상태 변경을 이벤트 로그로 기록해 장애 시 재처리 가능하다.
- 대규모 트래픽 환경에서 확장성이 뛰어나다.

---

## 4. 결론

- 도메인별 서버와 DB 분리는 확장성과 장애 격리 면에서 바람직하다.
- 하지만 여러 DB에 걸친 원자성과 정합성 보장이 어렵다.
- 이를 해결하기 위해 SAGA 패턴, Outbox 패턴, 보상 트랜잭션을 조합해 최종 일관성을 확보해야 한다.
- 장기적으로는 CQRS와 이벤트 소싱을 도입해 확장성과 복구 능력을 강화할 수 있다.
